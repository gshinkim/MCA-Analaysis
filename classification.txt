SKILL ROUTER: A CLASSIFICATION MODEL THAT RECOMMENDS WHICH SKILLS TO LOAD
Design plan, 2026-09-22 (revised: Jev first, Laya later)
==========================================================================


1. THE IDEA IN ONE PARAGRAPH
----------------------------
Before the AI model (local Ollama/LM Studio model or Claude) starts working, and
again after every tool call on the local path, a classification model reads
what the user asked and what the agent has already done. It returns, for each
Skill (mca, pathway-modeling, tellurium), the probability that
the Skill is needed right now. High confidence means the Skill is loaded for
the model automatically. Medium confidence means the model is given a
one-line hint. Low confidence means nothing is said. The goal is fewer steps,
fewer wasted tokens and less context: the model stops guessing the Tellurium
API, stops loading Skills late, and stops loading Skills it does not need.

The classifier is TypeSafe's Jev, called over its HTTP API with the user's
own API key. It is switched on and off, and the key is entered, in the app's
Settings dialog. Off by default.


2. WHY THIS HELPS (WHAT IS WRONG TODAY)
---------------------------------------
Today Skill routing is a fixed paragraph, SKILL_NOTE (web/js/prompt.mjs:54),
added to every message. It tells the model to "use the Skills as much as
possible". Whatever the request, the model has to decide for itself which Skill
to load and when. What goes wrong:

  a) Wasted steps. A model that never read the tellurium Skill invents the API.
     The team measured five failed guesses (loadAntimonyModel, Simulator,
     SBMLReader...) before one worked. The existing apiHint in
     backend/local-agent.mjs:170 only fires AFTER the failure. The router can
     prevent it before the first step.

  b) Context overflow on local models. Each SKILL.md is 7 to 13 KB (about 2 to
     3.5k tokens), 42 KB for all four. A comment in local-agent.mjs records
     that three Skills overflowed a 24k window. The router loads only what is
     needed.

  c) Cost and latency on Claude. Every Skill tool call is a full model turn. If
     the router already knows the request is plainly "simulate this model",
     the tellurium Skill can go into the first prompt and that turn is saved.


3. THE CLASSIFIER: JEV (TYPESAFE)
---------------------------------
Jev is a "System One" decision model. It never writes text. You give it:
  - a STATE: text or JSON (here, the request plus the agent's progress)
  - typed QUESTIONS: "noul" (a yes/no probability), "choice" or "score"
and it answers every question in one call. Because it returns numbers and
not text, there is nothing to parse and nothing to hallucinate.

  API (from TypeSafe's docs and the dev.to guide):
    POST https://api.typesafe.ai/v1/systemone
    Authorization: Bearer sk-...        (key from console.typesafe.ai/settings/keys)
    Content-Type: application/json

    Request:
      {
        "model": "jev-1.13.0",
        "state": { ... },
        "questions": {
          "tellurium": { "type": "noul",
                         "instructions": "Does the next step need ..." },
          "mca":       { "type": "noul", "instructions": "..." }
        }
      }

    Response:
      {
        "answers": {
          "tellurium": { "type": "noul", "noul": 0.87 },
          "mca":       { "type": "noul", "noul": 0.12 }
        },
        "model": "jev-1.13.0",
        "usage": { "input_tokens": 426 }
      }

  Facts that matter here:
  - Context window: 32,000 tokens, so the state can hold the full request
    and a real summary of what the agent has done (section 6).
  - Speed: about 70 to 500 ms end to end (third-party benchmarks measured
    236 to 276 ms p50), plus the network.
  - Cost: $0.042 per million INPUT tokens; output is free. A routing call
    is about 500 to 1,500 input tokens, so roughly 1,000 to 20,000 calls
    per dollar. The local path routes after every tool round, so a
    12-step turn costs about 13 calls, which is still a fraction of a cent.
  - Pin the version ("jev-1.13.0", not "jev-latest"). The thresholds in
    section 4 are tuned against one version, and "latest" can shift under
    them.
  - Privacy: the user's request and short tool summaries are sent to
    TypeSafe. The model source and file contents are NOT sent (section 6).
    The Settings text says so next to the switch.

  Laya (open weights, Apache 2.0, https://huggingface.co/convaiinnovations/laya)
  stays the planned local/offline alternative. Its README says the base
  checkpoint is near chance zero-shot until fine-tuned, so it is left for
  later. The router is written so the provider is one small function
  (section 5). Adding Laya later means adding a second function and a
  "provider" dropdown, with nothing else changing.


4. HOW A RECOMMENDATION IS USED (THREE TIERS)
---------------------------------------------
For each Skill that is NOT already loaded, the router returns p = P(needed).

  p >= AUTO   (default 0.85)   -> auto-load: the SKILL.md text is put into
                                  the model's input directly; no tool call
                                  is needed.
  p >= HINT   (default 0.50)   -> hint: one line is added:
                                  [router] likely needed: tellurium (0.91),
                                  mca (0.74). Load with load_skill / Skill.
  p <  HINT                    -> silent.

  Settings has a separate "Auto-load" switch, OFF by default. While it is
  off, everything at or above HINT is only a hint. Turn it on once the eval
  (section 9) shows the router is precise at 0.85. A wrong auto-load costs
  2 to 3.5k tokens of context. A wrong hint costs about 20 tokens, which is
  why hints come first.

  Rules that do not change:
  - The modelGate hard rule (pathway-modeling must be loaded before any write
    to the model, backend/local-agent.mjs:180) stays exactly as it is. The
    router only ADDS help and never removes a guard.
  - A Skill already loaded is never recommended again.
  - At most 2 Skills are auto-loaded per message, so context stays bounded.
  - If the router is off, has no key, gets an HTTP error (401, 429, 5xx),
    or takes longer than 2 s, the turn goes ahead exactly as today, with
    SKILL_NOTE only. Routing can never fail or block a turn. A bad key is
    reported once as a log line ("router: Jev rejected the API key") so the
    user knows why nothing is happening.


5. WHERE IT RUNS
----------------
  No Python and no new process: Jev is one HTTPS call, made from Node with
  the built-in fetch.

  New file: backend/router.mjs (small)
    - jev({ key, state, questions, signal }) -> { tellurium: 0.87, ... }
      The only Jev-specific code: builds the body, POSTs, reads
      answers[k].noul. It throws on HTTP errors or bad JSON.
    - route({ cfg, request, loaded, recent, hasModel })
        -> { auto: [...], hint: [...], ms, error? }
      Builds the state and the questions, calls jev() with a 2 s timeout,
      and applies decide(). It catches every error and then returns
      { auto: [], hint: [] }.
    - decide(p, loaded, cfg): the threshold logic as a pure function, so it
      can be tested without the network.
    - hintLine(hint) and autoBlock(auto, root): turn a decision into the text
      the model sees. autoBlock reads skills/<name>/SKILL.md the same way
      load_skill does.

  Questions are built once per server start from the skills/ folder (see
  section 6), then cached. A new Skill folder needs a restart, the same as
  skills/index.json today.


6. WHAT THE CLASSIFIER SEES (THE STATE)
---------------------------------------
Jev has a 32k window, but cost is per input token and short states are
judged more sharply, so the state is kept to about 1k tokens:

  {
    "request":  "<user message, trimmed to 2,000 chars>",
    "loaded":   ["pathway-modeling"],
    "recent":   ["load_skill pathway-modeling -> ok",
                 "write_file model.txt -> ok",
                 "run_python -> AttributeError: 'RoadRunner' object has no attribute 'getCC2'"],
    "model":    "has model" | "empty",
    "step":     3
  }

  "recent" is the last 6 tool calls as one-liners: tool name, main argument
  (a file path or Skill name, never file contents or a whole script), and
  for failures the first line of the error. This is the "feed it what it
  has currently done" part: an AttributeError mentioning RoadRunner should
  push tellurium up, and a write to the model should push pathway-modeling
  up.

  The QUESTIONS are one "noul" per Skill. The instruction is that Skill's
  own "description:" from the SKILL.md frontmatter, with a fixed lead-in:

    "tellurium": {
      "type": "noul",
      "instructions": "Given the request and what the agent has already done,
        will the agent's NEXT steps need the 'tellurium' Skill? That Skill
        covers: <description from skills/tellurium/SKILL.md>"
    }

  Adding a Skill folder therefore adds a question with no code change.


7. WHEN IT RUNS ON EACH PATH
----------------------------
  Local agent (runtime "openai", backend/local-agent.mjs):
    We own the loop, so we route at every step:
    - Before step 0: route on the request alone.
    - After each round of tool results: route again with the updated
      "recent" and "loaded". A round that loaded no new Skill and produced
      no error is skipped (no call), which saves most calls on long turns.
    - A hint is added to the end of the last tool-result message (appended
      text, not a new message), so the chat structure the local server
      sees is unchanged.
    - An auto-load runs the existing load_skill implementation for that
      Skill and adds its result, so tools.loaded (and therefore modelGate)
      treats it as a normal load.
    Both loops that run tools need the call: toolLoop (about line 293) and
    the second step loop (about line 499).

  Claude path (runtime "claude-code", backend/agent.mjs via server.mjs:506):
    The Claude CLI runs its own tool loop, so we cannot step in mid-turn
    without a hook. v1 routes ONCE per message, before the turn:
    - hint -> the line is appended to the prompt, after SKILL_NOTE
    - auto -> the SKILL.md text is appended too, with a note that the Skill
      is already loaded and must not be loaded again
    Mid-turn routing for Claude (a PostToolUse hook that calls the router)
    is left out of v1.

  Hosted browser agent (web/js/agent.mjs, only when the site is hosted):
    Not covered in v1. It would need the browser to call Jev directly, which
    exposes the key to the page and depends on Jev allowing CORS. The
    Settings switch says "local and Claude runtimes only".

  On the server, the pre-turn call happens in the POST /api/chat handler
  just before runAgent / runLocalAgent (server.mjs:503-507). The route
  config is passed into runLocalAgent so it can route again after tool rounds.


8. SETTINGS (TURN IT ON/OFF, ENTER THE KEY)
-------------------------------------------
  Where settings live today: the Settings dialog (web/index.html:226) keeps
  everything in the browser's localStorage under "settings"
  (web/js/settings.mjs, store.get/store.set). Endpoint API keys already
  live there, and the dialog already says "Tokens stay in this browser".
  They are sent with each chat request. The router follows the same
  pattern, so the key is never written to workspace/ or to git.

  New defaults in DEF (web/js/settings.mjs:20):
    router: { enabled: false, key: '', auto: false }

  UI: on the existing "Runtime" tab, under the workflow switch, add a small
  "Skill router (Jev)" section using the same markup the tab already uses:
    [switch] Recommend Skills with Jev
             "Before each step a TypeSafe Jev call estimates which Skills the
              agent needs and tells it. Sends your request and a short list of
              the agent's recent steps to TypeSafe. Local and Claude runtimes
              only."
    [password field] Jev API key   (placeholder "sk-...", link to
                                    console.typesafe.ai/settings/keys)
    [button] Test  -> calls POST /api/router/test, shows "Key works (230 ms)"
                      or the error, the same way the endpoint Test button
                      works (settings.mjs:237)
    [switch] Auto-load confident Skills (>= 0.85)   off by default
  The key field and the auto-load switch are greyed out while the main
  switch is off.

  Request: web/js/chat.mjs adds router: settings().router to the /api/chat
  body (next to chatCfg). The server reads it in the POST /api/chat handler
  (server.mjs:395), ignores it when enabled is false or key is empty, and
  never logs the key.

  New route: POST /api/router/test { key } runs one fixed routing call
  ("simulate this model for 100 seconds", which should say tellurium) and
  returns { ok, ms, p } or { ok: false, error }.

  Visibility: every routing decision is sent to the chat as the existing
  "log" event, for example:
    router 231ms: hint tellurium 0.91, mca 0.74 | auto none
  so the user can see what it did. The lines also land in the CLI stream
  logs, where they can be collected into eval cases.


9. PROVING IT WORKS (THE EVAL)
------------------------------
  New file: backend/router-eval/cases.jsonl
    About 60 hand-labelled cases, one per line:
      {"state": {...}, "need": ["tellurium"]}
    Mix of: first-message requests (build a model, simulate, compute control
    coefficients, explain a theorem, off-topic chat) and mid-turn states
    (after a model write, after an API error, after an MCA result). The
    logs opus/sonnet/haiku.jsonl are each a single session, too few to be a
    dataset, but they are a good source of realistic mid-turn states.

  New file: backend/router-eval/run.mjs
    JEV_API_KEY=sk-... node backend/router-eval/run.mjs
    Runs every case through route() and prints, per Skill, the precision
    and recall at 0.50 and 0.85, plus median latency and total input
    tokens (so we know the cost). The run costs well under one cent.

  Pass bars:
    - Hints useful:   recall >= 0.8 at 0.50 (it rarely misses a needed
                      Skill).
    - Auto-load safe: precision >= 0.9 at 0.85 (it rarely loads the wrong
                      one). Until this passes, leave Auto-load off.
    - Latency:        p50 < 600 ms from this machine.

  Also compare against a keyword baseline ("control coefficient" ->
  mca, "simulate" / "antimony" -> tellurium) in the same script. If Jev
  does not clearly beat it, the keyword rules are the simpler answer: free,
  instant, and nothing leaves the machine.

  If Jev misses the bars: reword the question lead-in first (free), then
  consider fine-tuning Laya on these same cases.


10. TESTS
---------
  - backend/router.test.mjs (runs in the normal test run, no network):
      decide(): auto / hint / silent, loaded Skills skipped, maxAuto cap,
        auto-load switch off turns every auto into a hint
      hintLine / autoBlock text
      route() with a fake fetch: returns empty on timeout, on 401, on 500,
        and on malformed JSON; parses answers[k].noul correctly
      questions are built from SKILL.md descriptions
  - backend/local-agent.test.mjs: with a fake router, an auto-loaded Skill
    shows up in tools.loaded and satisfies modelGate; a hint is appended
    to the tool result; router off means the loop is byte-for-byte the
    same as today.
  - The eval in section 9 is the real quality test. It needs a key and the
    network, so it is run by hand.

12. ORDER OF WORK
-----------------
  1. router.mjs + router.test.mjs (pure logic, fake fetch).
  2. Settings UI + /api/router/test. You can now paste a key and see it
     work.
  3. cases.jsonl + run.mjs. Run the eval. This is the go / no-go point
     for trusting it.
  4. Wire the local agent (hints, plus auto-load when switched on).
     Compare step counts on a few real requests with the router on and off.
  5. Wire the Claude path (once per message).


13. OUT OF SCOPE FOR V1
-----------------------
  - Laya (local, offline). Planned as a second provider behind the same
    route().
  - The hosted browser agent path.
  - Mid-turn routing on the Claude path (needs a CLI hook).
  - Recommending specific reference files inside a Skill. This could be a
    second-level "choice" question later.
  - Choosing which AI model to use (local vs Claude). The router picks
    Skills, not models.
